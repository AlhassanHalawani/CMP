# FR-016 — Mobile App Experience and Role-Based Bottom Navigation

**Priority:** High
**Status:** Planned (the web app works on mobile, but it should feel like a proper phone-first app without changing the existing desktop experience)

---

## Summary

Optimize the mobile version of CMP so students, members, club leaders, and admins can use the app comfortably from a phone.

This feature focuses on two major improvements:

- making the app installable from the landing page as a phone home-screen shortcut
- adding a mobile-only bottom navigation bar with quick access to the most important role-based actions

The installed shortcut should open CMP in a full-screen app-like mode, without the browser search/address bar when the device supports Progressive Web App behavior.

The desktop version must keep its current layout and navigation.

---

## Goal

Make CMP feel natural on mobile devices.

The mobile experience should answer:

- How can users open CMP quickly from their phone home screen?
- How can users reach their most common actions with one tap?
- How can role-specific workflows stay fast on small screens?
- How can mobile improvements be added without disturbing desktop users?

---

## V1 Product Scope

### In scope

- mobile-only install shortcut button on the landing page
- PWA manifest and install behavior needed for phone home-screen launch
- full-screen or standalone app display mode where supported by the browser/device
- mobile-only bottom navigation bar
- role-based bottom navigation items
- quick access to attendance QR scanning
- quick access to create event for club leaders
- quick access to club/member surfaces for students and members
- responsive spacing so main content is not hidden behind the bottom bar

### Out of scope for V1

- native iOS or Android app
- push notifications
- offline-first data sync
- replacing the desktop sidebar/header navigation
- changing desktop page layouts
- custom app-store distribution
- advanced mobile gestures

---

## Product Rules

### Desktop protection rules

- desktop layouts must not visually change as part of FR016
- existing desktop navigation should remain the primary navigation on desktop widths
- the bottom navigation bar must be hidden on desktop/tablet-wide layouts
- mobile-specific CSS should be scoped with clear breakpoints or mobile-only components

### PWA install rules

- the landing page should show an install/add-to-home-screen button only when useful
- if the browser supports the install prompt, the button should trigger it
- if the browser does not support the install prompt, the UI should show a short device-specific fallback instruction
- once installed, CMP should open in `standalone` or `fullscreen` display mode where supported
- the app must include a valid web manifest with app name, icons, start URL, theme color, and display mode
- the app must include mobile meta tags needed for iOS home-screen behavior

### Bottom navigation rules

- bottom navigation appears only on mobile authenticated app screens
- bottom navigation should use familiar icon buttons with short labels
- the center action should be visually emphasized
- navigation items must be role-aware
- the selected/current section should be visibly active
- bottom navigation should respect safe-area insets on modern phones
- page content should include bottom padding so important controls are not covered

---

## Recommended Mobile Navigation Model

Use five bottom navigation slots:

```txt
[ left 1 ] [ left 2 ] [ center action ] [ right 1 ] [ right 2 ]
```

The center action should represent the highest-value quick action for that role.

### Student / member

Recommended items:

| Slot | Item | Target |
|---|---|---|
| Left 1 | Feed/Home | `/feed` or student home |
| Left 2 | My Club | joined clubs or club detail |
| Center | Scan QR | attendance scanner |
| Right 1 | Events | event discovery or my events |
| Right 2 | Profile | student profile |

### Club leader

Recommended items:

| Slot | Item | Target |
|---|---|---|
| Left 1 | Dashboard | leader dashboard |
| Left 2 | My Club | managed club page |
| Center | Create Event | event creation flow |
| Right 1 | Scan QR | attendance scanner |
| Right 2 | Events | managed events |

### Admin

Recommended items:

| Slot | Item | Target |
|---|---|---|
| Left 1 | Dashboard | admin dashboard |
| Left 2 | Clubs | club management |
| Center | Scan QR | attendance scanner or lookup |
| Right 1 | Events | event management |
| Right 2 | Users | user management |

If the current app does not have all exact target routes, the implementation should map each item to the nearest existing route and document any missing route as a follow-up.

## Phase 2 — Add PWA Manifest and App Shell Metadata

Add or update:

- `manifest.webmanifest` or equivalent project convention
- app icons in required sizes
- `theme_color`
- `background_color`
- `start_url`
- `scope`
- `display`
- mobile web app meta tags

Recommended manifest values:

```json
{
  "name": "CMP",
  "short_name": "CMP",
  "start_url": "/",
  "scope": "/",
  "display": "standalone",
  "theme_color": "#ffffff",
  "background_color": "#ffffff"
}
```

Use `display: "standalone"` for broad compatibility. Consider `fullscreen` only if the app shell is verified to work well without browser chrome on target devices.

## Phase 3 — Landing Page Install Button

Add a mobile-oriented install button to the landing page.

Behavior:

- listen for the browser `beforeinstallprompt` event where available
- store the deferred install prompt in client state
- show the install button when installation is available
- trigger the prompt when the user taps the button
- hide or disable the button after install is accepted
- detect standalone mode and do not show the install button when already installed

Fallback behavior:

- on iOS Safari, explain that the user can use Share then Add to Home Screen
- on unsupported browsers, show a simple message that the app can still be used in the browser

The fallback text should be concise and should not clutter the landing page.

---

## Phase 4 — Mobile Bottom Navigation Component

Create a reusable mobile bottom navigation component.

Recommended behavior:

- reads the authenticated user role
- computes the correct nav items for that role
- renders exactly five slots where possible
- emphasizes the center action
- marks the current route active
- uses icons plus short labels
- is keyboard accessible
- uses safe-area padding for iOS/modern phone screens
- is hidden above the selected mobile breakpoint

Recommended implementation notes:

- place the component in the shared app layout, not inside individual pages
- avoid duplicating role logic across many pages
- keep route definitions centralized in a small config object
- use existing icon library if the frontend already has one

---

## Phase 5 — Route Mapping and Role-Specific Actions

Connect each bottom navigation item to real app routes.

Priority actions:

- `Scan QR` should open the fastest available attendance scanning route
- `Create Event` should open the event creation page for club leaders
- `My Club` should open the user's joined club or managed club context
- `Events` should open the most relevant event list for the role
- `Profile` should open the student's profile

Rules:

- if a member belongs to one club, `My Club` may go directly to that club
- if a member belongs to multiple clubs, `My Club` should open a club list or selector
- if a club leader manages one club, `My Club` may go directly to that club
- if a club leader manages multiple clubs, `Create Event` should either ask for the club or use the existing creation flow
- users should never see a bottom-nav action they are not authorized to perform

## Phase 6 — Mobile Layout Polish

Polish the mobile app shell after the bottom bar is added.

Required checks:

- bottom bar does not cover form buttons, event CTAs, or scanner controls

- modals and sheets remain usable with the bottom bar present

- install button does not compete with primary landing page CTA

- labels do not wrap awkwardly on narrow phones

## Acceptance Criteria

### PWA install acceptance criteria

- A mobile user can add CMP to the phone home screen from the landing page flow.
- The app includes a valid web manifest linked from the HTML/app shell.
- The manifest includes app name, short name, start URL, scope, display mode, theme color, background color, and icons.
- When launched from the home screen on supported devices, CMP opens in standalone/full-screen app mode without the normal browser search/address bar.
- The landing page does not show the install button when the app is already running in standalone mode.
- Unsupported browsers receive a concise fallback instead of a broken install action.

### Mobile navigation acceptance criteria

- Authenticated mobile users see a bottom navigation bar.
- Desktop users do not see the bottom navigation bar.
- Existing desktop navigation and page layout remain visually unchanged.
- The bottom bar contains five role-aware slots where possible.
- The center action is visually emphasized.
- Club leaders can quickly access `Create Event` from the center action.
- Students/members can quickly access `Scan QR` from the bottom bar.
- Club members and club leaders can quickly access `My Club`.
- Admins see admin-relevant shortcuts only.
- Users never see shortcuts for actions their role cannot access.
- The active route is clearly indicated.
- The bottom bar respects mobile safe-area spacing.
- Page content is not hidden behind the bottom bar.

### Quality acceptance criteria

- Mobile navigation labels fit on narrow phone screens.
- Bottom navigation remains usable with touch input.
- All bottom navigation buttons have accessible names.
- Keyboard focus states are visible.
- QR attendance scanning remains usable on mobile after layout changes.
- No new horizontal scrolling is introduced on common mobile widths.
- Existing tests pass, or any unrelated failing tests are documented.

## Implementation Notes for AI Agent

- Start by locating existing role and route definitions before creating new ones.
- Prefer a single bottom-nav configuration object keyed by role.
- Keep mobile-only styling isolated so desktop is protected.
- Use CSS media queries or existing responsive utilities rather than runtime screen-size guesses where possible.
- Reuse existing authentication and authorization guards.
- Reuse existing QR scanner and event creation routes instead of creating duplicate pages.
- If exact target routes are missing, add TODO notes in the implementation summary rather than inventing large unrelated flows.
